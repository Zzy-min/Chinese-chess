## 1. Executive Summary

本轮从真实用户视角出发，以“初次访问者”、“准备完成一盘棋的普通用户”、“异常与移动端场景用户”三条核心旅程贯穿，对轻棋局公开在线站点进行了全链路体验与工程诊断。

### 1.1 核心对局链路现状判断
**【可完成但存在明显体验缺陷与交互阻断风险】**
* **走通的部分**：公开站点已具备完整的注册/登录、创建房间、邀请码加入、准备就绪、双人实时在线对弈（WebSocket 广播）、双方棋盘视角自适应反转（红正黑倒）、回合倒计时、着法移动动画与刷新恢复能力。
* **阻断与受损部分**：
  1. 异常房间/对局 ID 会直接导致前端陷入**每秒 5 次的无限递归请求死循环**（无友好 404 或返回大厅引导），极易触发限流并造成页面雪崩；
  2. 远程对手认输或结束时，**获胜方页面完全不弹出胜利结算弹窗**，仅页面静默变灰，严重缺失胜负仪式感与复盘/再来一盘引导；
  3. 下棋非法走子或误点非己方棋子时，**错误提示瞬间被定时刷新循环刷掉**，用户得不到有效反馈；
  4. 移动端（390×844）及桌面常见分辨率（1280×800）下，**对局底部核心操作区域与玩家卡被截断或推至首屏视口之外**；
  5. 棋谱记法直接暴露底层行列数组坐标（如 `7,1 -> 7,4`），完全背离传统中国象棋记谱心智。

### 1.2 缺陷分布总览
* **P0 Blocker**: 1 项（路由异常与非法 ID 导致无限递归死循环请求）
* **P1 Critical**: 3 项（远程玩家无结算弹窗、非法走子错误提示被刷写吞掉、移动端棋局核心卡片切屏）
* **P2 Major**: 5 项（棋谱坐标暴露、桌面 1280 视口折叠线下截断、英文与后端异常直吐、原生 `confirm` 阻塞、公屏未审核不雅词）
* **P3 Minor**: 4 项（横幅山水图平铺拼接裂痕、房主多余“加入房间”按钮、空白棋格缺少无障碍语义、端间导航文案不一致）

### 1.3 前端视角最高优先级（Top 3～5）
1. **修复异常路由加载死循环守卫**：增加加载失败状态记录，避免 `loadRoom`/`loadGame` 失败后重复触发 `render()` 导致请求风暴。
2. **打通 WebSocket 实时结束事件与结算弹窗（Modal）**：在局部更新后补充 `maybeOpenEndGameModal` 触发，确保获胜方与观战方同步获得对局结果弹窗。
3. **解耦走子错误反馈与全局对局状态**：通过独立浮动 Toast、棋盘格震动或专用错误状态槽，保留非法移动真实原因。
4. **重构对局页自适应高度与安全区计算**：修正桌面 1280×800 和手机 390×844 的视口预算，确保棋盘、操作栏与玩家卡 100% 留存于首屏。
5. **记谱中文化与系统文案去技术化**：将内部坐标转换为传统“炮二平五”记谱法，全量翻译 `invalid credentials`、`RESIGN` 等裸露英文字符。

### 1.4 最值得保留的产品亮点
1. **极佳的国风视觉基调与微交互质感**：纸质暖色背景（`#fcfaf6`）结合朱砂红与黛绿，棋子立体质感细腻，落子翻转动画（FLIP）轻盈流畅。
2. **极轻量的网络负载与闪电首屏**：去重型框架设计，纯原生 JS + CSS，总资源体积仅 ~480KB，DOM 加载仅 300ms 级别。

## 7. P0 Issues

### ISSUE-001 — 访问不存在的房间/对局 ID 触发前端每秒 5 次递归请求死循环且 UI 永久白板

- **严重度**：P0 Blocker
- **修复优先级**：Fix Now
- **Owner**：agy（前端路由加载保护）
- **状态**：已验证事实
- **用户旅程阶段**：Journey C（异常与边缘场景）
- **影响平台**：Desktop / Mobile 全端
- **影响用户**：所有通过失效链接、错误邀请码或直接输入错误 URL 访问房间/对局的用户

#### 问题描述
当用户访问一个不存在或已过期的房间（例如 `#room/invalid-room-999`）或对局（`#game/invalid-game-id`）时，前端页面卡在“房间加载中”，同时以大约每秒 5 次的频率无限向后端发送 `GET /online/api/rooms/invalid-room-999` 请求。UI 没有任何错误提示，没有“返回大厅”按钮，控制台无阻断，用户完全无法自愈。

#### 前置条件
- 用户处于登录状态（或未登录直接访问带 ID 的路由）；
- 访问不存在的房间或对局 URL。

#### 可复现步骤
1. 登录轻棋局站点；
2. 在浏览器地址栏输入：`https://www.xiangqiarena.com/online#room/invalid-room-999`；
3. 打开 DevTools Network 面板观察；
4. 观察页面内容与网络请求。

#### 实际结果
- 3 秒内网络面板连续产生 15 次 `GET https://www.xiangqiarena.com/online/api/rooms/invalid-room-999` 请求（状态码 400 `{"error":"room not found"}`）；
- 页面中间只有一个卡片标题显示“房间加载中”，没有任何重试、返回大厅或错误说明按钮；
- 持续停留会迅速消耗用户的浏览器资源，并在 1～2 分钟内耗尽客户端或 IP 维度的请求频次配额。

#### 期望结果
- 当接口返回 `room not found` 或 404/400 时，停止发起重试；
- 页面展示友好的国风空状态插画或错误卡片：“该房间不存在或已解散”；
- 提供主操作按钮：“返回对局大厅”或“创建新房间”。

#### 用户影响
真实用户在微信或外部聊天软件中点击一个已解散的棋局分享链接时，会误以为“网站崩溃卡死”，并且因为持续的死循环发包导致手机发热发烫、后续正常请求被限流阻断。

#### 影响范围
所有点击过期链接、输错房间号或对局已彻底归档的用户。

#### 证据
- **代码根因**：`app.js` 第 1732-1737 行与 3836-3839 行：
  ```javascript
  function renderRoom(roomId) {
    const room = state.room;
    if (!room || room.roomId !== roomId) {
      loadRoom(roomId); // 触发异步加载
      return '<section class="panel"><h2 class="sectionTitle">房间加载中</h2></section>';
    }
  ...
  async function loadRoom(roomId) {
    state.room = await fetchJson(`${API_BASE}/rooms/${roomId}`).catch(() => null);
    render(); // 失败后置 null，继而 render()，render() 再次判断 !room 触发 loadRoom，构成无限死循环
  }
  ```
- **测试记录**：`verify_infinite_loop.js` 验证 3 秒收到 15 次连续请求。
- **截图**：`scratch/screenshots/infinite_loop_room.png`

#### 修复方向
在 `state` 中增加 `routeLoadError` 状态标记：
1. `loadRoom` 捕获异常后，记录 `state.routeLoadError = { type: 'room', id: roomId, message: '房间不存在或已关闭' }`；
2. 在 `renderRoom` 中，若检测到针对该 `roomId` 的加载错误，不再调用 `loadRoom`，直接渲染包含“返回大厅”按钮的错误面板；
3. 对 `renderGame`、`renderPractice`、`renderAnalysis` 实施相同保护机制。

#### 依赖
纯前端路由与状态机改造，无外部依赖。

#### 验证方法
在地址栏输入 `#room/nonexistent_test`，确认 Network 面板仅产生 1 次 400 请求即终止，UI 正确展示“房间不存在”卡片及“返回对局大厅”跳转链接。

## 8. P1 Issues

### ISSUE-002 — 获胜方在对手认输或结束时未收到 WebSocket 结算弹窗触发，页面静默冻结

- **严重度**：P1 Critical
- **修复优先级**：Fix Now
- **Owner**：agy（联合 Pi）
- **状态**：已验证事实
- **用户旅程阶段**：Journey B（结束棋局并查看结果）
- **影响平台**：Desktop / Mobile 全端
- **影响用户**：所有在联网对局中通过对手认输、超时或正常杀绝获胜的用户

#### 问题描述
在双人在线对弈中，当一方点击“认输”后，认输方本地会弹出“对局结束：胜方 黑棋”的结算弹窗（包含“进入分析”、“回到房间”等选项）；然而，通过 WebSocket 接收广播的另一方（获胜方），界面虽然将状态徽章变更为 `FINISHED`，但**完全没有弹出结算弹窗**，界面无声静止，没有任何“获胜！”庆祝态或下一步行动指引。

#### 前置条件
- 两个账号分别在两台设备（或独立浏览器上下文）中进入同一个在线对局。

#### 可复现步骤
1. 玩家 A（红方）与玩家 B（黑方）开始对弈；
2. 玩家 A 点击“认输”，并在浏览器确认对话框中点击确定；
3. 观察玩家 A（认输方）屏幕；
4. 观察玩家 B（获胜方）屏幕。

#### 实际结果
- 玩家 A（认输方）：成功弹出浮层弹窗《对局结束》，包含胜方、结束原因、进入分析、回到房间按钮；

  ```javascript
  if (previousGame && state.game && previousGame.gameId === state.game.gameId
  ```

- **代码根因**：`app.js` 第 3971-3974 行：
  ```javascript
  function refreshLiveStatusLine(route = currentRoute()) {
  ```

前端 UI 状态层。

#### 验证方法

- **事实状态**：已验证事实
- **用户价值**：整站摒弃了 React/Vue 等重型前端运行时包袱，纯原生轻量化构建。主脚本 `app.js` 约 223KB，样式表 `app.css` 约 210KB，首屏 HTML 仅 1KB，且无复杂第三方广告和冗余字体包。
- **证据**：真实测量 DOMContentLoaded 仅 311ms，首屏整体加载仅 322ms（无缓存条件），页面切换秒级响应。
- **为什么值得保留**：超轻体积对弱网环境、移动网页对局至关重要，保证了下棋对决的轻快心智。

### HIGHLIGHT-003 — 实时对局红黑视角自动智能反转 (Smart Perspective Flip)
- **事实状态**：已验证事实
- **用户价值**：在线对弈建立后，系统根据玩家分配的阵营自动旋转棋盘坐标：红方在下时楚河汉界居中且正向，黑方在下时将帅九宫位于底部且“汉界 楚河”相应翻转，双方操作均符合己方视角直觉，且 WebSocket 坐标反转映射无缝无误。
- **证据**：`host_game_screen.png`（红方底视视角）与 `guest_game_screen.png`（黑方底视视角）对比验证。
- **为什么值得保留**：解决了许多简陋在线棋类网站只能固定红方在下的硬伤。

### HIGHLIGHT-004 — 移动端专有 Shell 架构与刷新状态自愈能力
- **事实状态**：已验证事实
- **用户价值**：不仅为手机屏幕量身打造了类似原生 App 的底部导航栏（首页/对局/学习/观战/我的）和“⚡ 快速开局”轻量抽屉，而且当玩家在对局或 AI 练习中意外刷新网页时，页面能精准根据 URL 哈希恢复棋局快照，不丢失对局上下文。
- **证据**：`mobile_after_reload.png` 验证刷新后棋局瞬间恢复。
- **为什么值得保留**：大幅提高了移动端浏览器的抗意外中断能力。

```text
Mobile Readiness: Partial (部分可用，但对局页面存在物理视口溢出缺陷)
```

### 14.1 移动端亮点
- 针对移动端定制了专属的界面布局（`mobileHome`, `mobileLobby`, `mobileBottomNav`），未生硬缩放桌面页面；
- 底部 Tabbar（首页/对局/学习/观战/我的）图标设计精致，符合手机端原生交互直觉；

### 14.2 移动端核心硬伤（已通过自动化真机视口验证）
1. **对局视口高度溢出（ISSUE-004）**：在 390×844（iPhone 13 标准屏）下，对局桌上下纵向元素累计高度超过屏幕，底部玩家卡片有一半被裁切在可视区外，必须上下滑动。

3. **未登录跳转盲区**：移动端首页点击“客”字头像跳转到个人中心时，直接呈现一个缺乏关闭返回引导的空白表单，用户极易困惑。

## 17. Trust & Safety Findings (信任与安全观察)

   - 页面底部缺少常见的产品运营说明、服务条款（Terms of Service）与隐私政策（Privacy Policy）链接；虽在“帮助”页提供了玩法说明，但未提供明确的用户支持/问题反馈渠道邮箱或入口。
