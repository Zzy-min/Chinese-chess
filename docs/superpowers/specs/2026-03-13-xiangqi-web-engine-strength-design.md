# Xiangqi Web 端棋力提升设计

## 1. 背景与目标

本设计聚焦 `XiangqiGame` 的网页端（`WebXiangqiServer`）人机对战棋力提升，目标是在不新增前端配置项的前提下，提升象棋对局质量与稳定性。

已确认目标：
- 覆盖两条技术线：内置 AI + Pikafish 外部引擎。
- 优先级：先提升内置 AI，再完善外部引擎协同。
- 端范围：仅网页端。
- 体验策略：`EASY/MEDIUM` 保持流畅，`HARD` 明显加强。
- 验收方式：胜率基准 + 固定局面质量基准。

## 2. 范围与非目标

### 2.1 本期范围

- 调优 `MinimaxAI` 的难度预算与搜索阈值（参数级改动）。
- 调优 `PikafishUciEngine` 的难度映射参数与超时恢复策略。
- 复用并增强基准工具，形成可回归比较的验证产物。
- 保持网页 API 协议与交互行为兼容。

### 2.2 非目标

- 不新增网页高级设置项（例如手动输入深度、时间、Hash）。
- 不重写搜索框架（不做算法架构级替换）。
- 不覆盖桌面端 Swing 控制流改造。

## 3. 现状摘要

核心调用链（网页象棋 PVC）：
- `WebXiangqiServer` 在 AI 回合触发异步搜索。
- `ConfigurableXiangqiEngine` 按偏好选择 `BuiltinXiangqiEngine` 或 `PikafishUciEngine`。
- 外部引擎失败时已具备内置回退，随后还有首合法着法兜底。

当前优势：
- 具备完整回退链，稳定性底座已存在。
- `MinimaxAI` 已有迭代加深、PVS、TT、LMR、Null Move、时间压力 EMA 等能力。

当前问题：
- 难度分档预算仍有进一步拉开空间，`HARD` 强度提升不够稳定。
- Pikafish 映射参数较保守，且恢复策略仍可细化到分阶段超时。
- 缺少“固定局面质量”维度的稳定回归工具。

## 4. 方案对比与结论

候选方案：
1. 参数调优优先（本期采用）
2. 自适应引擎动态切换（暂缓）
3. 离线大规模参数搜索管线（暂缓）

采用方案 1 的原因：
- 变更集中在现有边界内，风险和回归成本可控。
- 可在当前代码结构下快速验证收益。
- 与“本期只做网页端、后台自动调优”的约束完全一致。

## 5. 架构与模块边界

### 5.1 `MinimaxAI`（内置引擎强度线）

职责：
- 在既有搜索框架下，重设难度预算与阈值，使 `HARD` 在关键局面获取更高质量。

改动原则：
- 仅做参数和预算调优，不引入新搜索框架。
- `EASY/MEDIUM` 保持时延上限，`HARD` 允许适度增加预算。

重点改动位：
- `Difficulty` 基础预算（深度/时间）
- `tuneBudget(...)` 动态预算规则
- 与 `searchFastMode` 相关的阈值协调

### 5.2 `PikafishUciEngine`（外部引擎强度与稳定线）

职责：
- 提供外部引擎搜索能力，并在异常时快速失败返回供上层回退。

改动原则：
- 优化分档参数映射：`movetime/depth/skill/hash/threads`。
- 超时控制分层：初始化、ready、bestmove 各阶段独立超时。
- 任何异常都应短路退出并可恢复，不阻塞主流程。

### 5.3 `ConfigurableXiangqiEngine`（路由与回退线）

职责：
- 管理引擎偏好与实际选择，外部失败时回退内置。

改动原则：
- 保持现有对外接口。
- 增强失败状态描述（用于服务端状态和调试）。

### 5.4 `WebXiangqiServer`（对局执行线）

职责：
- 维持 AI 异步调度和兜底流程。

改动原则：
- 不改 `/api/new`、`/api/endgame`、`/api/state` 协议。
- 必要时仅补充轻量统计字段或日志，不影响前端兼容性。

### 5.5 基准工具（验证线）

职责：
- 提供版本间可重复对比。

改动项：
- 复用 `AIBenchmarkMain` 进行胜率/时延采样。
- 新增固定局面质量基准工具（建议 `XiangqiFenQualityBenchmarkMain`）。

## 6. 运行数据流

网页 PVC 象棋主流程：
1. 前端通过 `/api/new` 提交难度与引擎偏好。
2. `WebXiangqiServer` Session 保存 `difficulty + engine preference`。
3. AI 回合异步调用 `xiangqiAI.findBestMove(snapshot, aiColor, difficulty)`。
4. 若外部引擎失败或返回无效着法，回退 `BuiltinXiangqiEngine`。
5. 若仍失败，使用首合法着法兜底，确保对局继续。
6. `/api/state` 返回当前引擎状态与对局状态供前端轮询展示。

## 7. 错误处理与稳定性策略

### 7.1 分阶段超时

- `uci` 初始化超时。
- `isready/readyok` 超时。
- `bestmove` 等待超时。

任一阶段超时：
- 关闭进程句柄。
- 当前请求返回 `null`。
- 交由上层回退逻辑继续。

### 7.2 无效着法防护

- 外部返回走子必须经过合法性校验。
- 非法结果视同失败，进入回退链。

### 7.3 流畅性保护

- `EASY/MEDIUM` 设置严格时延上限。
- `HARD` 放宽但设硬天花板并受时间压力 EMA 约束，避免极端长考。

## 8. 测试与验收标准

### 8.1 胜率与耗时（AIBenchmarkMain）

对比调优前后：
- `HARD vs MEDIUM` 胜率提升。
- `EASY/MEDIUM` 平均思考时长增幅受控。

建议阈值：
- `HARD vs MEDIUM` 胜率提升 >= 5%。
- `EASY/MEDIUM` 平均时长增幅 <= 15%。

### 8.2 固定局面质量（新增 FEN 基准）

- 构建开局/中局/残局代表局面集。
- 记录首选着一致率、战术命中率或目标着法命中率。
- 验收：`HARD` 指标提升，`EASY/MEDIUM` 不显著劣化。

### 8.3 稳定性

- 模拟 Pikafish 不可用、异常退出、超时。
- 验收：不出现对局卡死，回退链可持续提供合法着法。

## 9. 风险与缓解

- 风险：`HARD` 参数过激导致响应抖动。
  - 缓解：先小步调参 + 基准回归，逐项放开预算。
- 风险：Pikafish 参数不兼容不同二进制构建。
  - 缓解：参数发送容错 + 失败即回退。
- 风险：仅凭胜率提升可能掩盖局部走子质量退化。
  - 缓解：引入固定 FEN 质量基准作为硬门槛。

## 10. 实施边界结论

本设计已满足：
- 单一子系统范围（网页象棋引擎强度提升）。
- 清晰模块边界（内置、外部、路由、服务端调度、基准）。
- 具备可执行且可验证的验收标准。
